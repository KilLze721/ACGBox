# 管理端账号自身编辑

## 访问规则

- 仅供已登录的 ADMIN、EDITOR 使用，不开放游客或 USER 管理端访问。
- 所有请求携带 `Authorization: Bearer <JWT>`。
- 操作账号 ID 和令牌版本取自 JWT，不接受请求指定其他账号。
- 不允许修改用户名、角色、启用状态，只支持修改自己的密码和邮箱。
- 修改密码需要当前密码，邮箱绑定、换绑、解绑均不需要输入密码。
- 不返回密码哈希，不记录明文密码、验证码或邮箱换绑凭证。
- 无需修改数据库表结构，也不会自动执行 SQL。

## 启用邮件验证码

新增依赖为项目现有 Spring Boot 版本对应的 Spring Mail 和 Spring Data Redis。
Redis 保存验证码摘要、短期换绑凭证摘要和发送限流计数，管理端认证仍使用 JWT 和数据库 token_version。

在后端运行配置中设置以下环境变量，不要将实际授权码提交到 Git：

| 环境变量 | 含义 | 默认值 |
| --- | --- | --- |
| ACGBOX_ACCOUNT_EMAIL_ENABLED | 是否启用邮件验证码 | false |
| ACGBOX_MAIL_HOST | SMTP 服务器地址 | 空 |
| ACGBOX_MAIL_PORT | SMTP 端口 | 587 |
| ACGBOX_MAIL_USERNAME | SMTP 认证账号 | 空 |
| ACGBOX_MAIL_PASSWORD | SMTP 密码或服务商授权码 | 空 |
| ACGBOX_MAIL_FROM | 发件地址，必须符合服务商发件规则 | SMTP 认证账号 |
| ACGBOX_MAIL_STARTTLS | 是否启用且强制要求 STARTTLS | true |
| ACGBOX_MAIL_SSL | 是否使用隐式 TLS | false |
| ACGBOX_REDIS_HOST | Redis 地址 | localhost |
| ACGBOX_REDIS_PORT | Redis 端口 | 6379 |
| ACGBOX_REDIS_USERNAME | Redis ACL 用户名 | 空 |
| ACGBOX_REDIS_PASSWORD | Redis 密码 | 空 |
| ACGBOX_REDIS_DATABASE | Redis 数据库编号 | 0 |

使用 SMTP 587 时通常启用 STARTTLS；使用 465 时通常设置 MAIL_SSL=true、MAIL_STARTTLS=false，最终以服务商要求为准。
SMTP 和 Redis 均设置了连接与读写超时，SMTP 未启用时不影响查询自身账号或修改密码。
配置后重启后端，再进行实际收信测试；未配置时接口返回明确业务错误，不会假装发送成功。
生产环境接口必须通过 HTTPS 提供，并将 Redis 部署在受控网络、配置访问认证。

## 查询自己的账号

`GET /admin/account`

无需请求体，返回现有 UserAccountVO，包括 id、username、email、role、enabled、emailVerifiedAt、createdAt、updatedAt。

## 修改密码

`POST /admin/account/change-password`

```json
{
  "currentPassword": "old-password",
  "newPassword": "new-password"
}
```

当前密码必须正确，新密码不去空格、不转换大小写，最多 72 个 UTF-8 字节。
新旧密码相同时不更新数据库，也不递增版本；实际修改后旧令牌全部失效，需要重新登录。

## 首次绑定邮箱

先调用 `POST /admin/account/email/code`，发送到待绑定的新邮箱：

```json
{
  "purpose": "BIND",
  "email": "New@Example.com"
}
```

收到验证码后调用 `POST /admin/account/email`：

```json
{
  "email": "New@Example.com",
  "newEmailCode": "123456"
}
```

示例验证码只是格式示例，必须替换为实际收到的验证码。
首次绑定不传 emailChangeToken。绑定后设置 emailVerifiedAt，并递增 token_version。
若已有邮箱但 emailVerifiedAt 为空，也可用相同邮箱执行此流程完成验证。
邮箱保持大小写，唯一性和邮箱密码登录继续区分大小写。

## 换绑邮箱

换绑不需要密码，严格按照“验证原邮箱 → 验证新邮箱 → 完成换绑”进行。
原邮箱验证成功时不解除绑定，也不递增版本；新邮箱验证并保存成功后才替换原邮箱。

### 第一步：向原邮箱发送验证码

`POST /admin/account/email/code`

```json
{
  "purpose": "CHANGE"
}
```

CHANGE 的接收地址从数据库读取，前端无法指定原邮箱地址。

### 第二步：验证原邮箱，获取换绑凭证

`POST /admin/account/email/verify-current`

```json
{
  "currentEmailCode": "654321"
}
```

成功响应示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "emailChangeToken": "替换为接口返回的实际换绑凭证",
    "expiresIn": 300
  }
}
```

原邮箱验证码验证成功后立即消费；凭证有效期五分钟，仅限当前账号、当前令牌版本和当前原邮箱。
凭证不是登录 JWT，前端仅暂存于当前换绑流程，不替换 Authorization 请求头，也不要打印或存入 URL。

### 第三步：向新邮箱发送验证码

`POST /admin/account/email/code`

```json
{
  "purpose": "BIND",
  "email": "New@Example.com",
  "emailChangeToken": "替换为第二步返回的实际换绑凭证"
}
```

后端先校验换绑凭证，再向新邮箱发信；不能跳过原邮箱验证直接发信。
发送新邮箱验证码不会延长换绑凭证有效期，也不会消费凭证。

### 第四步：验证新邮箱，完成换绑

`POST /admin/account/email`

```json
{
  "email": "New@Example.com",
  "newEmailCode": "123456",
  "emailChangeToken": "替换为第二步返回的实际换绑凭证"
}
```

最终提交不再传 currentEmailCode，改为携带第二步取得的 emailChangeToken。
后端校验凭证和新邮箱验证码，再一次性消费凭证并保存邮箱，令牌版本递增后需重新登录。
新邮箱验证码错误时保留尚未过期的换绑凭证；凭证过期时需重新从第一步开始，旧邮箱仍保留。
仅修改邮箱字母大小写也视为换绑，需要完成上述流程。
原邮箱无法访问时不提供绕过接口，应由管理员通过现有账号管理流程处理；唯一 ADMIN 的恢复需要部署者另行核验身份。

## 解绑邮箱

先调用 `POST /admin/account/email/code` 向原邮箱发信：

```json
{
  "purpose": "UNBIND"
}
```

再调用 `POST /admin/account/email/unbind`：

```json
{
  "verificationCode": "654321"
}
```

解绑只验证原邮箱验证码，无需密码；将 email、emailVerifiedAt 显式写为 null，保留用户名和密码，之后仍可用用户名密码登录。

## 验证码与令牌规则

- 验证码为 6 位数字字符串，保留开头的零。
- 有效期 5 分钟，同一账号同一用途每 60 秒可发送一次，所有用途合计每小时最多 10 次。
- 每条验证码最多允许 5 次错误尝试，达到上限即失效。
- 验证码绑定账号 ID、令牌版本、用途和大小写保持原样的邮箱，不能混用。
- Redis 保存 HMAC-SHA256 摘要，不保存明文验证码或换绑凭证；摘要按用途区分，与 JWT 签名内容不共用数据格式。
- 换绑凭证由 32 字节安全随机数编码生成，有效期五分钟；同一账号、版本和原邮箱仅保留最近一次签发的凭证，最终换绑时一次性消费。
- Lua 脚本原子执行限流、错误计数与单次消费；同一账号的键使用相同 Redis Cluster 哈希槽。
- 发送失败会尝试删除本次验证码摘要，但保留发送限流，重试仍需等待冷却。
- 同一邮箱重新发送会替换旧验证码；不同邮箱、不同用途的验证码分别保存。
- 任何退出登录、密码修改或其他版本变化都会使之前版本下的验证码和换绑凭证无法再用于编辑账号。
- 发送验证码和换绑前验证原邮箱不递增 token_version，密码实际修改、邮箱绑定、验证未验证的已有邮箱、最终换绑或解绑会递增版本。
- 验证码与换绑凭证消费不能随 PostgreSQL 事务回滚；若凭证到期、唯一性或并发检查失败，需要重新获取已消费的验证码或凭证，数据库原邮箱不会被提前清空。
- 成功修改后不重新签发 JWT，前端清理本地登录状态并跳转登录页；其他设备在下次请求时收到 401。

成功响应沿用 `Result.success()`；参数校验和业务错误沿用项目现有 Result 格式，认证失败仍为 HTTP 401、角色不足为 HTTP 403。

## 验证范围

自动化测试覆盖自身账号隔离、角色限制、密码校验、免密码邮箱操作、旧邮箱验证与换绑顺序、凭证范围和消费、邮箱唯一性、绑定与解绑字段、并发版本冲突、旧 JWT 失效、验证码摘要和发送故障。
测试中数据库、Redis 和 SMTP 均使用模拟对象，不会修改真实账号或实际发邮件；Redis Lua 运行和邮件实际投递需要在配置真实服务后联调。
